# PR, CI и автодеплой

Решение владельца 03.10.2026: агент заканчивает задачу готовым PR. С 07.10.2026 после самопроверки и зелёного CI агент мержит PR сам (`gh pr merge --squash`), отдельного ревью владельца нет. После мержа всё, что крутится в облаке, выкатывается само. Если владелец попросил только PR без мержа, агент останавливается на PR.

## 1. Как агент готовит PR

1. **Ветка.** От свежего `main` (`git fetch && git switch -c <тема> origin/main`). Прямо в `main` не коммитить. Коммиты маленькие, по ходу работы.
2. **Самопроверка до PR** (обязательна, PR без неё не открывается):
   - тесты и `typecheck` всех затронутых частей (команды в [AGENTS.md](../AGENTS.md#команды)); новая логика с тестом;
   - изменённое запущено по-настоящему, а не только тестами: ядро локально и запрос к изменённому маршруту, iOS в симуляторе и `DesignScreenshots` при правке интерфейса;
   - ревью собственного диффа (`/code-review` или вручную построчно): ошибки, крайние случаи, утечки секретов в код и логи, совместимость с данными на томе `/data` (старые `memory.json`, `tasks.json` и др. должны читаться);
   - всё найденное исправлено, документы обновлены (правила в [AGENTS.md](../AGENTS.md#жёсткие-правила)), строка в [test-protocol.md](test-protocol.md) для новой функции;
   - готовность к проду: новые переменные окружения заведены в Railway до мержа (иначе ядро выкатится без них), миграция данных описана, откат понятен.
3. **PR.** `git push -u origin <ветка>`, `gh pr create`. В описании: что и зачем; как проверено (команды и итог); что не проверено (например, «на iPhone не проверено»); риски и откат; что нужно сделать владельцу (до мержа такой PR не мержится). PR привязать к треду (`link_pull_request`).
4. **Зелёный CI на PR.** Дождаться `gh pr checks --watch`; красный чинить в той же ветке.
5. **Мерж.** `gh pr merge <номер> --squash`, затем дождаться «Verify deploy» (раздел 2) и сказать владельцу, что выкатилось. Нельзя мержить, если что-то из PR требует действий владельца до мержа (переменные Railway, токены): тогда PR ждёт его.

## 2. Что происходит после мержа

```
merge в main → GitHub Actions «CI» (тесты) → зелёный → Railway собирает и выкатывает → «Verify deploy» сверяет /health
```

- **CI** (`.github/workflows/ci.yml`): на каждый PR и на `main`. Ядро: `npm ci`, `typecheck`, `npm test`. Части, которых PR не касается, пропускаются. iOS в CI нет: macOS-раннеры в приватном репозитории дорогие, тесты iOS прогоняет агент до PR.
- **Деплой**: встроенная интеграция Railway с GitHub. Сервис `volna` (до 21.10.2026 `core`) следит за `main`, корень `/core`, срабатывает только на изменения в `/core/**`, «Wait for CI» включён: Railway ждёт, пока все проверки GitHub Actions на коммите пройдут; красный CI деплой не запускает. Пока новая версия не прошла проверку `/health`, работает старая. Из-за тома одновременно две копии не работают: около минуты ядро недоступно.
- **Проверка** (`.github/workflows/verify-deploy.yml`): по успешному деплою Railway ждёт, пока `/health` вернёт `commit`, равный смерженному коммиту (ядро берёт его из `RAILWAY_GIT_COMMIT_SHA`), и `ready: true`. Красная проверка значит: выкатилось не то или ядро без ключей.
- **Почта** (`mail-triage`): свой репозиторий, та же схема ([railway.md](railway.md)).
- **helm-cloud** (сервис `helm`) и «Узел»: свой репозиторий `~/Documents/Projects/helm-cloud`, деплой и установка «Узла» описаны там.
- **iOS** ставится из Xcode, как раньше.

## 3. Если деплой сломался

Railway → `Helm` → сервис → Deployments → прошлый удачный → Rollback. Или `git revert` смерженного PR новым PR: после мержа выкатится прежний код. Данные на томе откат не трогает.
