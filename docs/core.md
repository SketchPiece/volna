# Ядро (core/)

Устройство ядра. До 27.09.2026 эта часть называлась «мостом» (bridge), 27.09.2026 ненадолго «сервером» (папка `server/`), теперь «ядро» (папка `core/`). От старых имён остались только сохранённые на устройствах ключи: `BRIDGE_TOKEN`, `CALL_ASSISTANT_BRIDGE_URL` и `CALL_ASSISTANT_BRIDGE_TOKEN`, ключ `bridgeURL` в UserDefaults, запись Keychain `CallAssistant.bridge`, а также имена в коде (`createBridge`, `BridgeOptions`). Общая картина и инварианты в [architecture.md](architecture.md); здесь только то, что нужно, чтобы менять и расширять ядро.

## 1. Роль

Ядро держит ключ OpenAI, собирает конфигурацию GPT-Live-сессии и обменивает SDP: `POST /v1/live/sessions` с `transport: { type: 'webrtc', sdp }`, в ответе SDP-answer и `session.id`. Звук идёт напрямую iPhone ↔ OpenAI. После ответа ядро подключается к той же сессии по sideband-WebSocket (`wss://api.openai.com/v1/live/sessions/{id}/attach`), обслуживает вызовы инструментов ядра и пишет транскрипт. Приветствие просит не ядро, а телефон после `session.started` (см. architecture.md, раздел о звонке): из ядра при открытии sideband Live откладывал его до первой реплики пользователя. Протокол `POST /session` для клиента не менялся при переходе с Realtime на Live (22.09.2026); изменились только допустимые голоса.

GPT-Live полнодуплексна: детектора речи нет, модель слушает и говорит одновременно, сама уступает пользователю. Инструменты она не зовёт: делегирование клиентское (`delegation: { type: 'client' }`), работу исполняет само ядро моделями OpenRouter ([4h](#4h-клиентское-делегирование)). До 23.09.2026 был и режим `delegation.responses` с бэкенд-моделью OpenAI (`gpt-5.6-luna`); он удалён по решению владельца.

Инструменты бывают двух видов по месту исполнения. Инструменты ядра (`runsOn: 'core'`, по умолчанию) исполняет ядро: время, память. Инструменты телефона (`runsOn: 'device'`: напоминания, календарь, контакты) ядро кладёт в очередь `/device-tools`, исполняет их приложение на iPhone ([4h](#4h-клиентское-делегирование)). Дизайн и причины: [design/volna-tools.html](design/volna-tools.html).

Через тот же sideband ядро записывает транскрипт звонка и ведёт долговременную память о пользователе (`src/memory/`, дизайн в [memory-design.md](memory-design.md)). Приложение управляет памятью через `/memory`.

## 2. Стек

- Node ≥ 22.18, TypeScript исполняется нативно (стирание типов), без сборки. Синтаксис только стираемый: без `enum`, `namespace` и параметров-свойств в конструкторах.
- [Hono](https://hono.dev) + `@hono/node-server`: маршруты и middleware. Выбран за малый размер, композицию middleware и то, что приложение тестируется как обычная функция.
- [zod 4](https://zod.dev): схемы аргументов инструментов (из них же генерируется JSON Schema для OpenAI) и проверка `.env`.
- WebSocket-клиент встроенный в Node (`globalThis.WebSocket`, принимает заголовок `Authorization`).

## 4. Поток вызова инструмента

1. `POST /session`: без `OPEN_ROUTER_API_KEY` ядро отвечает 503 до обращения к OpenAI (отвечать на делегирование некому). Приложение перечисляет в заголовке `X-Device-Tools` инструменты телефона с выданным доступом; `ToolRegistry.forDevice` оставляет инструменты ядра целиком и только объявленные инструменты телефона, при `WEB_SEARCH=on` ядро добавляет свой `web_search`. `buildInstructions(tools.names())` уходит голосовой модели (с 26.09.2026 без имён инструментов: по ним выбираются только правила, умения описаны словами; определений инструментов у Live нет), `buildBackendInstructions(tools.names())` получает модель делегирования.
2. Ответ `POST /v1/live/sessions` содержит `session.id`. Ядро открывает sideband `…/live/sessions/{id}/attach` с `Authorization: Bearer <ключ>`; при открытии ничего не шлёт (триггер приветствия отправляет телефон после `session.started`).
3. Live присылает `session.delegation.created`; `ClientDelegate` выбирает маршрут и модель, модель зовёт инструменты, ядро исполняет их через `SidebandControl.runTool` → `ToolRegistry.call(name, arguments, context)`. Инструменты телефона уходят в очередь `/device-tools` (4h).
4. Ответ модели уходит в Live `session.commentary.append`, голосовая модель его озвучивает.
5. Соединение закрывает OpenAI по окончании сессии (`session.closed` с причиной); страховка 2 часа. При закрытии сигнал идущих инструментов отменяется.

Ошибки инструмента (неизвестное имя, невалидные аргументы, исключение) возвращаются модели делегирования JSON-объектом `{ error: … }`, чтобы она честно сказала о сбое. Если `session.id` нет, звонок работает без делегирования, инструментов ядра и транскрипта, в лог пишется предупреждение.

## 4d. Завершение звонка Волной

`end_call` (`tools/end-call.ts`): модель делегирования зовёт его, когда пользователь прощается или просит закончить. Инструмент через `ToolContext.endCall` просит sideband закрыть сессию и возвращает ей указание попрощаться одной фразой. Sideband ждёт прощание: после первого фрагмента `session.output_transcript.delta` отсчитывает `farewellQuietMs` (2 с) тишины в транскрипте Волны, но не дольше `farewellMaxMs` (8 с) с момента запроса, затем шлёт `session.close`. Телефон получает `session.closed` с причиной `close_requested` и завершает звонок штатно, как при нажатии «Завершить». Без sideband инструмент отвечает `{ error: 'end_call_unavailable' }`.

## 4b. Поиск в интернете

Инструмент `web_search` ядра (`delegation/web-search.ts`), когда `WEB_SEARCH=on` (по умолчанию): модель `CLIENT_SEARCH_MODEL` с плагином OpenRouter `web` ([4h](#4h-клиентское-делегирование)). Правило «свежие и проверяемые данные, источники по просьбе» в `buildBackendInstructions`. До 23.09.2026 в режиме Responses был встроенный `web_search` бэкенд-модели.

## 4c. Инструменты телефона

`tools/device.ts` держит имена, описания и zod-схемы `create_reminder`, `list_reminders`, `complete_reminder`, `create_event`, `list_events`, `find_contact`, чтобы модель видела их в одном списке с инструментами ядра и чтобы контракт покрывался тестами. `execute` у них бросает: ядро их не исполняет. Приложение объявляет доступные имена в `X-Device-Tools` (неизвестные и невалидные имена отбрасываются, не больше 32); без заголовка сессия содержит только инструменты ядра. Swift-сторона контракта: `CallAssistant/Services/DeviceTools/DeviceToolContract.swift`; менять только парой.

## 4a. Память

1. `POST /session`: `MemoryService.context()` строит секцию инструкций по уровню близости (`cold` даёт пустую; тогда инструменты `remember/forget/recall` убираются из сессии через `ToolRegistry.without`). Транскрипция встроена в GPT-Live и отдельно не включается; на уровнях `attentive` и `involved` ядро просто создаёт `CallRecorder`.
2. Sideband передаёт каждое событие в `CallRecorder.observe`: берутся фрагменты `session.input_transcript.delta` и `session.output_transcript.delta` с `start_ms/end_ms`; реплика закрывается сменой говорящего, паузой длиннее 2 с или концом звонка.
3. После закрытия sideband `MemoryService.endCall`: если пользователь что-то сказал, транскрипт сохраняется в `data/transcripts/`, `extractFromTranscript` получает текущую память и диалог и возвращает операции `add/update/close` плюс профиль; они применяются как `inferred`, чувствительное отбрасывается без `allowSensitive`. Если «сна» не было сутки, следом идёт `dream`. Ошибки памяти логируются счётчиками и не влияют на звонок.
4. Инструменты: `remember` пишет как `explicit` (чувствительное разрешено, пользователь попросил сам), с `about` и `category` кладёт запись в карточку (заводит её, если нет); `forget` закрывает совпадения, с `whole: true` карточку целиком или все карточки категории; `recall` ищет по словам, включая закрытое, а если запрос называет карточку, отдаёт её целиком (`card`: суть, свои записи, связанные эпизоды и нити).

   Карточки (с 26.09.2026, [memory-design.md, 9](memory-design.md#9-карточки)): `memory.json` → `cards`, у записи `cards` (id, первая своя). Операции `card` и `merge_card` применяются раньше записей того же ответа, записи ссылаются на карточку по id или названию (`findCard`). REST: `cards` и `categories` в `GET /memory`, `DELETE /memory/cards/:id`. Промпт собирает `promptBlocks` в `context.ts`.
5. Нить для приветствия выбирается только на `involved`: прошедшая по дате, не чувствительная, не поднятая раньше. В инструкциях она называется по-человечески («Открытая тема, о которой спросить в начале: …»), потому что модель может повторить правило вслух. `askedAt` ставит не `MemoryService.context()`, а возвращённый им `commitThread()`, который `session-route.ts` зовёт после того, как OpenAI принял звонок (с 26.09.2026; до этого неудачная попытка сжигала нить). Перезвон по заданиям и звонок с неуслышанными итогами работы нить не выбирают (`context({ thread: false })`): она ждёт следующего звонка. Вопрос о нити в приветствии и есть тот один вопрос из памяти за звонок, который разрешает правило уровня `involved` (эта оговорка в правиле только при выбранной нити). Поднятая нить больше не выбирается.
6. Техкарты — скиллы в формате Agent Skills (`skills/`, папки `core/skills`, `data/skills`, `SKILLS_EXTRA_DIRS`, плагины; функции техкарт `always`). С 25.09.2026 техкарта — единица маршрута делегирования (4h): `techcard_read` (с `file` читает приложенный файл), `techcard_write` (целиком пишет раздел «Правила владельца», прежняя версия в `data/skills/.history.json`, до 10), `techcard_delete`. Список «название (описание)» идёт в инструкции бэкенда (`SkillStore.index` → `buildBackendInstructions`), а не голосовой модели. На `cold` техкарт в звонке нет. Извлечение и «сон» их не трогают. REST: техкарты в `GET /memory` (с `fresh` и `source`), `DELETE /memory/techcards/:name` (409 для встроенных); установка `npm run skills -- add`. Устройство: [skills.md](skills.md), поведение: [memory-design.md, 7](memory-design.md#7-техкарты).
7. Личный слой характера (`persona/`, файл `data/persona.json`): `PersonaStore` хранит слой и историю изменений, `PersonaReviewer.maybeReview` зовётся после извлечения и «сна» (`MemoryService.afterCall`), не чаще раза в 3 дня и только если с прошлого пересмотра есть 5 сохранённых разговоров. Модель та же, что у памяти. Слой встаёт в инструкции сразу после заводского характера (`personalLayer`), на `cold` не применяется. `PERSONA_REVIEW=off` выключает пересмотр. Дизайн: [memory-design.md, 8](memory-design.md#8-личный-слой-характера).
8. История (`memory/history.ts`, техкарта `core/skills/history`, класс `standard`): `history_read` читает, что было в прошлых звонках и заданиях. С `day` (`YYYY-MM-DD`) берутся все звонки этого дня по `TIME_ZONE`. Имя файла транскрипта содержит дату UTC, поэтому читаются соседние даты, а день проверяется по `startedAt`. Без `day` с `query` берутся до трёх последних звонков о теме. Без `day` и `query` берётся последний сохранённый звонок. Выдержки занимают не больше ~4000 символов на ответ: с запросом это подходящие реплики с соседними (`score`/`tokens` из `memory/store.ts`), без него начало и конец разговора. Из `tasks.json` приходят задания, созданные или законченные в этот день (или подходящие к запросу): название, статус, короткий итог. Если уровень ниже `attentive`, в ответе есть `note`, что разговоры не сохраняются; если ничего не найдено, `note` просит не выдумывать. На `cold` `history_read` убирается из сессии вместе с памятью (`HISTORY_TOOL_NAMES`). Текст разговора уходит только модели и в лог не пишется.

Файлы памяти в `core/data/` (в `.gitignore`); путь меняется `MEMORY_DIR`. Модели памяти идут через OpenRouter (ключ `OPEN_ROUTER_API_KEY`): извлечение после звонка `MEMORY_MODEL` (по умолчанию `anthropic/claude-sonnet-5`), «сон» и пересмотр характера `MEMORY_DEEP_MODEL` (`anthropic/claude-opus-5.5`). Замер 25.09.2026 на трёх настоящих звонках, тот же промпт и схема: GPT-5 Mini заводил дубль уже существующей нити, Haiku 4.5 терял даты эпизодов и выдумывал предпочтения, Gemini 3.5 Flash Lite терял нити. Sonnet 5 аккуратнее всех, около $0,01 за звонок. Opus 5 находил самые полезные выводы («завершать разговор после „всё, спасибо“»), но чаще додумывал, поэтому ему достались только редкие «сон» и пересмотр характера; вместо Opus 5 взят Opus 5.5 (решение владельца). Живая проверка через код ядра: извлечение 15 с, «сон» 19 с, обе схемы приняты.

## 4f. Замеры задержек

Каждый звонок пишет `data/metrics/<время>-<звонок>.json` (выключается `METRICS=off`, каталог `METRICS_DIR`): настройки звонка (модели, режим Jev; в старых файлах ещё `reasoning` и `service_tier` бэкенда Responses) и события с временем прихода в ядро в мс от подключения sideband. Инвариант лога сохраняется: ни текста разговора, ни аргументов и результатов инструментов; от транскрипта только `start_ms/end_ms` и длина фрагмента, от бэкенда тип события, имя инструмента, статус и токены (в том числе `reasoning_tokens`), потоковые дельты только первая на элемент. Неизвестные события пишутся по типу: так видно, какие события Live реально присылает в sideband (не всё подтверждено документацией).

Отметки ядра: `tool.start/tool.end` (источник `client` или `jev`; в старых файлах `backend`), `tool.output.sent` (только в старых файлах), `jev.request/jev.result/jev.error`, `prefetch.sent/prefetch.dropped`, `endcall.armed/confirmed/cancelled`, `session.close.sent`.

`npm run metrics` делит события на ходы (фраза пользователя → реакция) и печатает p50/p90 по группам настроек: `speak` (конец фразы → первый звук ответа, главная цифра), `decide` и `decideAudio` (решение Live делегировать; второе по часам сессии без сети), `select`, `resume` и `backend` (только звонки через бэкенд Responses до 23.09.2026), `tool`, по каждому инструменту отдельно, и совпадение Jev с бэкендом. `-- --csv` отдаёт ходы для таблиц, `-- --since 2026-09-23` отсекает старые звонки. Конец фразы считается по приходу последнего фрагмента транскрипта, поэтому включает задержку транскрипции; сравнивать настройки между собой корректно, абсолютные цифры нет.

До 23.09.2026 скорость бэкенда Responses задавали `BACKEND_REASONING` и `BACKEND_SERVICE_TIER`; удалены вместе с режимом. Скорость делегирования теперь задаётся выбором моделей класса (`CLIENT_MODEL_*`).

## 4g. Jev: раннее завершение

Jev (TypeSafe AI, System One) не пишет текст: отвечает на заранее заданные вопросы вероятностями за 300–600 мс. Ключ: `TYPESAFE_API_KEY` (`api.typesafe.ai`, модель `jev-latest`) или `OPEN_ROUTER_API_KEY` (тот же протокол `POST https://openrouter.ai/api/v1/systemone`, модель `typesafe/jev-1.13`); при обоих берётся TypeSafe. Режимы `JEV_MODE`: `on` (по умолчанию при ключе, решение владельца 22.09.2026) действует, `shadow` только пишет решения в замеры, `off`.

`GoodbyeWatcher` (`jev/goodbye.ts`): через 350 мс тишины во входной стенограмме Jev отвечает, прощается ли пользователь. При вероятности ≥ `JEV_GOODBYE_THRESHOLD` (0.9, до 23.09.2026 было 0.93) `endCall('prefetch')` взводит то же завершение, что `end_call` (тишина 2 с после прощания Волны, максимум 8 с), и Live получает «Ядро: пользователь прощается». Если пользователь заговорил снова, завершение отменяется и Live получает поправку; если модель делегирования сама позвала `end_call`, отменить нельзя. На звонках 22.09.2026 срабатывало верно (0.93–0.97), «пока не надо» давало 0.03. 22.09 «Ладно, всё, спасибо большое» получило 0.89 и не сработало, поэтому порог снижен, а в критерии добавлено «всё» + благодарность; ближайший ложный кандидат «Пока. Не надо ничего. Подожди секунду» давал 0.88.

С 26.09.2026 вечером: предел ожидания Jev в клиенте 3 с (было 1,5 с; маршрут и честность ждут меньше своим сигналом): в тот вечер Jev отвечал 0,9–1,4 с, и «Ничего, пока» осталось без ответа. Пока идёт работа и в звонке есть `tasks_call_back`, тем же запросом Jev отвечает на `callback` (прощание с просьбой перезвонить, `CALLBACK_GOODBYE_QUESTION`): при уверенности ≥ `JEV_GOODBYE_THRESHOLD` ядро само зовёт `tasks_call_back` и взводит завершение, Live получает «перезвон уже записан, попрощайся» (действие `callback` в `jev.result`). Раньше такой ход шёл через модель делегирования тремя кругами, 9–13 с до конца звонка. В делегировании после успешного `end_call` ядро больше не зовёт модель ради прощальной фразы: Live получает готовую просьбу попрощаться (путь `farewell`, `farewellCommentary` в `delegation/client.ts`), а бэкенду велено звать `tasks_call_back` и `end_call` в одном ответе. На звонках не проверено.

Замеры приветствия (`telemetry/greeting-probe.ts`, 26.09.2026): на каждую команду «поздоровайся» до первой реплики ядро пишет `greeting.trigger` с уровнем входного звука за секунду до неё (дБ от полной шкалы, считается из `session.input_audio.append` в sideband), затем `greeting.said` с задержкой или `greeting.silent`, если за 4 с Волна не заговорила; сводка в `npm run metrics`. Звук и текст в замеры не пишутся. Ошибка сокета sideband после `session.closed` — обычный конец звонка (`sideband dropped after session closed`), предупреждение только для ошибки до него.

Предвыборка инструментов в режиме Responses удалена 22.09.2026 по замерам: Live делегирует через 0,1–0,8 с после фразы, Jev отвечает позже, а справку в `session.thinking.append` Live не использует, пока ждёт свой бэкенд (ответ звучал только вместе с текстом бэкенда). Справка с `delegation_id` делегирования Responses вызывает `invalid_request_error` «unknown client delegation» и обрыв сессии. Выбор инструмента на Jev живёт в клиентском делегировании (4h).

## 4h. Клиентское делегирование

Единственный режим с 23.09.2026 (решение владельца; до этого эксперимент `DELEGATION=client` рядом с `responses`). Нужен `OPEN_ROUTER_API_KEY`, без него `/session` отвечает 503, а `/health` даёт `ready: false`. Сессия создаётся с `delegation: { type: 'client' }`, Live при нужде в работе присылает `session.delegation.created` без текста задачи, а `ClientDelegate` (`delegation/client.ts`) отвечает сам:

1. Ждёт до 400 мс хвост стенограммы (150 мс тишины во входе) и берёт реплики до последней реплики пользователя (`realtime/conversation.ts`).
2. Маршрут (с 25.09.2026 по техкартам, план и замеры в [tools-routing.md](tools-routing.md#техкарта--единица-маршрута-25092026)): один запрос к Jev (если `JEV_MODE=on`, ждём не дольше 800 мс; пока Jev в этом звонке ни разу не ответил, до 2 с: 25.09.2026 в начале звонка он отвечал за 0,8–1,4 с, позже за 0,3–0,4) задаёт вопросы `tool` (инструмент с карточкой `jev`: `current_time`, `about_wave`, `tasks_list`), `techcard` (техкарта маршрута из `skills/routing.ts`: встроенные `core/skills/*` и свои, у которых хотя бы один инструмент из `allowed-tools` есть в звонке; плюс `none` и `mixed`), `tier` (`simple|standard`), `missing` (чего не хватает: `what|when|who|which|nothing`; задаётся, если есть простая техкарта с меняющим инструментом) и `agree` (только когда Волна предложила работу: согласился ли пользователь). Порядок ответа: согласие ≥ 0.85 → ядро само запускает предложенное (`offer.start`); инструмент с вероятностью ≥ `JEV_TOOL_THRESHOLD` → ядро исполняет и отвечает без LLM (`jev`); простой техкарте с меняющим инструментом не хватает главного (≥ 0.8) → Live получает «не хватает: когда…», модель не зовётся (`ask`); иначе модель класса: `CLIENT_MODEL_SIMPLE` (по умолчанию `google/gemini-3.5-flash-lite`), `CLIENT_MODEL_STANDARD` (`openai/gpt-5.6-luna`, до 25.09.2026 `anthropic/claude-sonnet-5`), обе через `delegation/llm.ts` (модели `openai/*` с 29.09.2026 напрямую в Responses API OpenAI ключом `OPENAI_API_KEY`, `store: false`, цена по таблице `OPENAI_PRICES`, `CLIENT_OPENAI_DIRECT=off` возвращает их на OpenRouter; прямой запрос ждём 8 с, опоздание или ошибка — тот же запрос через OpenRouter, замер в [tools-routing.md](tools-routing.md); у OpenAI Luna с размышлениями и инструментами работает только через `/v1/responses`, так что OpenRouter ходил туда же, лишнее звено стоило ~0,1 с на круг и хвосты; остальные — OpenAI-совместимый `chat/completions` OpenRouter с `provider.sort: latency`, `max_tokens` 2000 вместе с размышлениями: при 600 размышления съедали предел, и вызов инструмента обрезался). Модель видит только `allowed-tools` выбранной техкарты, кроме скрытых (`hidden`, по умолчанию `current_time`: время уже в инструкциях, с 29.09.2026), инструменты `always` (`end_call`, `techcard_*`), служебные `escalate` и `offer_work`, а в системной инструкции текст техкарты (инструкции и правила владельца, до 3000 знаков). Уровень техкарты (`metadata.tier`) — нижняя планка класса. `none` даёт только `always`, `mixed` все инструменты. Техкарта и класс берутся при вероятности ≥ `JEV_ROUTE_THRESHOLD` (0.6); иначе, как и без Jev, `standard` со всеми инструментами; при ошибке или опоздании Jev `simple` со всеми инструментами (дальше `escalate`), чтобы простой вопрос не ждал Sonnet: 25.09.2026 «который час» на Sonnet с 23 инструментами занял два круга по 4,5–5 с. До 4 кругов, вызовы в круге параллельно. На классе `simple` успешное изменение с первого круга (все вызовы `write`, например напоминание) сразу уходит Live без второго круга модели (`fill`). `escalate`, ошибка модели или исчерпанные круги повторяют запрос со всеми инструментами и классом выше, но не после успешного меняющего вызова: повтор сделал бы действие дважды. Инструменты `startsWork` (`work_start`, `techcard_create`) модели не видны: она зовёт `offer_work { tool, arguments, summary }` (с `readOnly: true` задание, которое только смотрит, ядро запускает сразу, путь `offer.readonly`, см. [tools-routing.md](tools-routing.md)), ядро проверяет аргументы по схеме, запоминает предложение (10 минут или 3 делегирования) и просит Live предложить работу своими словами, каждый раз по-разному, без выбора между вариантами. На следующее делегирование Jev отвечает на `agree`; «да» запускает ровно предложенное (слова согласия длиннее трёх слов дописываются к `task`), «нет» (< 0.2) забывает предложение. Без Jev модель получает `start_offered_work` и зовёт его после явного «да». В системной инструкции текущее время, так что «завтра в девять» не требует `current_time`. Замер 25.09.2026 (без звонка, Jev через OpenRouter): выбор техкарты не теряет точности до 100 вариантов (41/42 при 40–101, p50 ~300 мс), `missing` 10/11, `agree` 7/7.
3. Ответ уходит `session.commentary.append` с `delegation_id` (≤ 1400 символов); при сбое короткая реплика о сбое. Новое делегирование отменяет незаконченное.

Промпт делегирования (с 25.09.2026). Инструкции собираются на каждый проход (`instructions` — функция от имён инструментов прохода вместе с инструментами запуска работы): правила только о том, что модель видит. Отдельного списка имён инструментов нет, правило о запуске работы одно (`backendOffer`). Память — `MemoryContext.backend`: без «Недавних разговоров», вместо них отсылка к `history_read`. В схемах инструментов нет `$schema` и повторов описаний внутри `anyOf` (`compactSchema` в `registry.ts`). На техкарте «Работа» промпт сократился с 16,7 до 12,2 тыс. знаков, со всеми инструментами — с 25,9 до 21,3 тыс. Замер 25.09.2026 (81 запрос к Sonnet 5 через OpenRouter, реплики из звонка): ни размер контекста (3,5–10,9 тыс. токенов), ни размышления (по умолчанию, выключены, `low`) скорость заметно не меняют, медиана 1,5–2,5 с, разброс 1–4 с. Сокращение даёт цену ($0,011 вместо $0,024 за запрос), а не скорость. В звонке того же вечера ход Sonnet был 4,5–5,4 с. Причина не установлена: все замеры ушли к провайдеру Azure, а какой провайдер отвечал в звонке, не записывалось. Поэтому `client.llm` в замерах теперь несёт `provider`, `gen` (id запроса OpenRouter) и `reasoningTokens`.

Поиск: ядро добавляет инструмент `web_search` (`delegation/web-search.ts`): модель `CLIENT_SEARCH_MODEL` с плагином OpenRouter `web`. Инструменты телефона идут через очередь ядра (`delegation/device-broker.ts`, маршруты `http/device-tool-routes.ts`, только с токеном ядра): ядро кладёт вызов, телефон во время звонка держит долгий опрос `GET /device-tools?wait=25000`, исполняет вызов тем же `DeviceToolRunner` и отвечает `POST /device-tools/:id { output }` (`CallAssistant/Services/DeviceTools/DeviceToolRelay.swift`, цикл в `CallCoordinator.startDeviceToolRelay`). Если телефон не забрал вызов за 15 с, модель получает `device_unavailable`, если забрал и не ответил, `device_timeout`. Ядро без ключа OpenRouter (или старое ядро) маршрута не имеет, телефон получает 404 и прекращает опрос до конца звонка. В каждом ответе опроса есть и `working`: id идущих заданий; `TaskStore.subscribe` будит опрос при каждом изменении задания (`DeviceBroker.notify`), по этому списку телефон включает музыку ожидания (эксперимент 26.09.2026, [architecture.md, 5](architecture.md)). Заголовок `X-Wait-Music: on` на `/session` добавляет голосовой модели правило «музыка без слов на телефоне — не пользователь» (`WAIT_MUSIC` в `persona.ts`, только при `work_start`). Очередь общая для идущих звонков: один пользователь и один телефон. Защита от выдуманных действий (`delegation/honesty.ts`): в системной инструкции запрет сообщать о действии без успешного вызова; кроме того, финальный ответ проходит широкий предфильтр по словам действия (`claimsAction`: «поставил», «записал», «напомню», «сделаю»; с 26.09.2026 и краткие причастия «создано», «записано», «добавлено в календарь», и начало дела «запускаю», «ищу», «займусь», «передал Клоду», «перезвоню»; вопросы, «я считаю» и отрицания «не создано», «не было отправлено» не считаются). Ответ без таких слов (поиск, разговор, «Сейчас десять») Jev не ждёт вовсе. Ответ со словами проверяет Jev (с 26.09.2026, вопрос `honesty` в `jev/questions.ts`), если в проходе не было успешного меняющего вызова или был и неудачный меняющий, не исправленный успешными повторами того же инструмента (`unrecovered`: успехов после неудач должно хватить на каждую неудачу, два упавших напоминания и один удачный повтор — одно несделанное; частичный успех: «Записал и отправил», когда отправка упала): он видит ответ и все вызовы прохода с их `effect` и успехом и отвечает, заявлено ли действие, которого вызовы не подтверждают. Порог `HONESTY_THRESHOLD` 0.7, а когда вызовов не было вовсе, `HONESTY_NO_CALLS_THRESHOLD` 0.4 (подтвердить заявление нечем); оба не откалиброваны на звонках; отметка `client.honesty.check` с `by: jev|words`, `p`, `ms`. Так ловится «Поставил» после одного `current_time`, а «Меня сделал Андрей» после `about_wave` нет. Jev ждём столько же, сколько в маршруте: `routeTimeoutMs`, а пока он в этом звонке ни разу не ответил, до `firstRouteTimeoutMs`. Без Jev, при его ошибке или опоздании решают слова (`claimsByWords`): ответ вовсе без вызовов или после одних неудачных меняющих вызовов («Отправил» после упавшей отправки); после читающих вызовов («Меня сделал Андрей» после `about_wave`) и при частичном успехе нет. Проверка стоит одного запроса к Jev (0,3–0,6 с), но только на ответ со словами действия. Если действие заявлено без подтверждения, ядро один раз возвращает ответ модели (служебным сообщением, помеченным «не от пользователя») с требованием вызвать инструмент или честно отказать, при повторе отдаёт Live честный отказ (`client.honesty` в замерах). При частичном успехе отказ не «ничего не получилось»: `honestyFallback` называет сделанное по-человечески («напоминание», «сообщение Клоду»; карта `DONE_TITLES`, без аргументов, незнакомые инструменты не называет) и просит сказать своими словами, что остальное не вышло, не произнося названий инструментов. Отказ без успехов нейтральный: «Бэкенд не выполнил действие» (вызов мог быть, но упасть). Повод: Gemini 22.09.2026 «поставил» напоминание без инструмента. Действием считается успешный вызов инструмента с `effect` не `read` по реестру (с 25.09.2026; прежний свой список читающих отстал, и после `techcard_read` пустой ответ сходил за «Готово.»).

План: [tools-routing.md](tools-routing.md), шаг 4 (22.09.2026). С 26.09.2026 большое дело одно: «Работа» (набор `work`), программирование тоже; «Код» в Claude Desktop (`agents_*`) удалён. Долгую работу бэкенд не делает в разговоре: с 25.09.2026 он зовёт `offer_work`, Волна предлагает её своими словами (каждый раз по-разному), и после «да» ядро само запускает `work_start` (`tasks/tools.ts`, `act`, `startsWork`; 4h). С `HELM_TOKEN` исполнитель — «Штурвал» (4l): исследование, план, разбор, действия в приложениях Mac. Прежние `task_start` (исполнитель на Opus с читающими инструментами и поиском) и `computer_start` сведены в него. С 23.09.2026 Волна не спрашивает, как сообщить итог, и сама перезвон не предлагает (решение владельца). Ещё есть `tasks_list` (читает, есть карточка Jev; показанные итоги считаются услышанными; у идущих заданий отдаёт `progress`), `task_cancel` и `tasks_call_back`: пользователь просит перезвонить (обычно прощаясь: «перезвони, как всё будет готово»), и всем идущим и ждущим доставки заданиям ставится `callback: call`. Jev не считает такое прощание концом звонка, пока просьба не записана (`jev/questions.ts`). С вечера 26.09.2026 концом разговора считается и просьба перезвонить без «пока» («перезвони, когда закончится»), если к ней не добавлено новой просьбы или вопроса: Jev отвечает на неё `callback`, а бэкенду велено звать `tasks_call_back` и `end_call` в одном ответе (звонок 26.09.2026: Волна сказала «перезвоню» и не положила трубку). У перезвона свой порог `CALLBACK_THRESHOLD` 0.75 (`jev/goodbye.ts`): на пробе Jev (9 фраз × 3) такие просьбы получали 0.89–0.92, у общего порога 0.9 это через раз, а самое высокое «нет» («а ты можешь перезванивать?») 0.38; 25 из 27 при 0.9, 27 из 27 при 0.75. На звонках не проверено. Включается, когда есть ключ OpenRouter (для сводок хода), `PULT_URL` и `TASKS=on` (по умолчанию).

1. `TaskRunner` (`tasks/runner.ts`): очередь, не больше двух заданий одновременно, не дольше 10 минут (в «Штурвале» — `HELM_TASK_MAX_MINUTES`, 4l). С 26.09.2026 исполнитель только `helmWorker` (4l), `pultComputer` ниже не подключается (Пульт deprecated, [task-sync.md](task-sync.md)). Единственный исполнитель `worker` — `pultComputer` (`tasks/computer.ts`): Codex (Астра) через `POST /computer` в Пульте; он сам ищет в сети, а приложения Mac открывает только если задание этого требует (промпт `ComputerJob.prompt` в Пульте). Проверено 23.09.2026: исследование «последняя версия Node.js» — ответ с источником за 11 с. Итог короткий, для пересказа голосом (до 2000 символов). Старые записи с `kind: think` только читаются. Хранилище `data/tasks.json` (`tasks/store.ts`, последние 50 законченных). Задания, прерванные остановкой ядра, при загрузке становятся `failed` с `interrupted`.
2. Ход работы (`tasks/progress.ts`, с 23.09.2026). Исполнитель по ходу пишет журнал в память: реплики Астры, сводки размышлений и действия из `activity` Пульта, ожидание кнопки на телефоне. Раз в `TASK_PROGRESS_SECONDS` (30 с, `0` выключает) дешёвая модель `TASK_PROGRESS_MODEL` (по умолчанию `google/gemini-3.5-flash-lite`, до 80 токенов) сворачивает новые строки каждого идущего задания в одну фразу. Фраза пишется в `Task.progress`. Нет новых строк — нет запроса. Журнал в лог и на диск не пишется.
3. `TaskDelivery` (`tasks/delivery.ts`) решает, как сообщить итог. Если идёт звонок, модель получает заметку `session.instructions.append` «Ядро: фоновое задание … готово» с просьбой сказать сразу, не дожидаясь паузы, даже если пользователь говорит (решение владельца 26.09.2026: итог важнее, он замолчит и выслушает; `announce(…, { urgent: true })`). Сама заметка Волну не озвучивает: в звонке 26.09.2026 с текстом «когда пользователь договорит» она молчала, пока владелец не спросил. Поэтому все заметки ядра просят сказать «сейчас, если пользователь молчит», а `LiveCalls` (`realtime/live-calls.ts`) после заметки слушает звонок: нет речи Волны 6 с и пользователь молчит 2 с (для итога работы пауза не нужна) — один раз шлёт короткую просьбу `ANNOUNCE_NUDGE` сказать сейчас (дольше 20 с не ждёт). Иначе итог ждёт, пока закончатся все задания (`waiting`). Потом все неуслышанные итоги (до пяти) уходят одной пачкой. Если хоть для одного просили перезвонить, ядро шлёт один VoIP-пуш (id первого задания, заголовок «Задания готовы» или название единственного), и телефон звонит голосом Волны. Не ответили за 45 с, тогда приходит одно уведомление. Иначе уведомление уходит сразу: у одного задания это название и первое предложение итога, у нескольких — список названий. Отмена задания тоже проверяет, не пора ли слать пачку. Если пушей нет или они не дошли, итоги ждут следующего звонка (`delivery: pending`).
4. Звонок Волны. Приложение получает VoIP-пуш `{ task, title }` (`PushRegistration`, PushKit), сразу показывает входящий через CallKit (`CallCoordinator.incomingCallback`, `CallKitCallService.reportIncoming`) и звонит 40 с. При ответе приложение открывает обычную сессию с заголовком `X-Callback-Task: <id>`. `tasks/context.ts` собирает правило начала звонка (`opening`) с итогами всей пачки (задания с `delivery: ringing`), и оно встаёт в инструкции на место правила приветствия: без «Да, слушаю» начать с «Перезваниваю по заданию» и своими словами рассказать, что сделано и какой результат: всего до пяти предложений, подробности по просьбе; о неудаче сказать честно, без предложения повторить. Приложение в таком звонке просит не «поздоровайся», а «начни звонок» по этому правилу (`RealtimeClient.callbackOpeningInstruction`); правило начинается теми же словами («Когда попросят начать звонок»). Перезвон не выбирает и не сжигает нить из памяти (4a, п. 5). Если итогов для перезвона нет (задание не найдено, не готово, id не прошёл проверку), звонок идёт как обычный: фраза приветствия, нить, `commit()`; просьба телефона на этот случай велит поздороваться по правилу приветствия. До пуша ядро сжимает итоги для голоса (`tasks/summary.ts`), в звонок идёт выжимка, а не отчёт агента целиком (26.09.2026: с сырым итогом и правилом приветствия рядом Волна отвечала «Да, слушаю» и молчала). В начало любого звонка попадают и неуслышанные итоги (до трёх), а также названия идущих заданий, чтобы Волна знала о них и не заговаривала сама. Итоги из этой секции Волна рассказывает сама, бэкенд о них не спрашивает; о ходе работы и об итогах, которых в инструкциях нет, спрашивает бэкенд (правило `TASKS` в `persona.ts`, согласовано 26.09.2026). После создания сессии итоги помечаются услышанными (ошибка записи уходит в лог).
5. Пуши (`push/apns.ts`): APNs по HTTP/2, токен провайдера ES256 из ключа `.p8`, обновляется раз в 50 минут. VoIP идёт с топиком `<bundle>.voip` и `apns-expiration: 0`, уведомление с обычным топиком и `time-sensitive`. Токены присылает приложение при каждом запуске: `POST /push/register { voip, alert, environment }` с токеном ядра (`http/push-routes.ts`). Ядро хранит их в `data/push.json` (`push/devices.ts`). Окружение `development` (сборка из Xcode, sandbox) или `production`. Ответ 410 или `BadDeviceToken` стирает токен. Без `APNS_KEY_PATH`, `APNS_KEY_ID` и `APNS_TEAM_ID` пушей нет, итоги говорятся в звонках. Настройка ключа: [device-setup.md](device-setup.md#перезвон-волны-и-уведомления-apns).

6. Таб «Работа» в Пульте (`tasks/pult-sync.ts`, с 23.09.2026; удалён из ядра 27.09.2026). При каждом создании и изменении задания (`TaskStore.onChange`) ядро шлёт Пульту `PUT /tasks/{id}` со снимком: название, вид, состояние, фраза хода, итог (до 600 символов), ошибка, время. Текст задания (prompt) не уходит. Снимки одного задания идут по очереди. Работа Астры запускается `POST /computer { text, ref }`, где `ref` — id задания ядра: по нему Пульт берёт название и фразу хода. Пульт выключен — снимки теряются, задания работают как раньше.

Главный экран телефона (с 26.09.2026, `http/task-routes.ts`). `GET /tasks` с токеном ядра отдаёт до 10 заданий, новые первыми: идущие и ждущие, с вопросом исполнителя и законченные за сутки; поля `id, title, status, waiting, progress, createdAt, startedAt, finishedAt`, без текста задания и итога. 8. Перезвон в назначенное время (`callbacks/`, 26.09.2026). «Перезвони в шесть и напомни про отчёт», «набери через полчаса»: бэкенд зовёт `callback_schedule { at | inMinutes, reason, title }` (`write`, техкарты «Планы» и «Работа»). `at` — ISO 8601; без смещения это местное время в поясе `TIME_ZONE` (`callbacks/time.ts`). Прошедшее время, дальше месяца и нечитаемое время отклоняются. Ещё `callbacks_list` (карточка Jev) и `callback_cancel`; перенос — отмена и новый. «Перезвони, когда будет готово» остаётся `tasks_call_back`; «перезвони в шесть и расскажи, что с работой» — перезвон по времени, о ходе работы Волна спросит бэкенд уже в звонке. Хранилище `data/callbacks.json`, последние 30 прошедших. `CallbackScheduler` держит один таймер на ближайший перезвон и взводит его заново после каждого изменения и при старте ядра. Когда время пришло: идёт звонок — срочная заметка «Ядро: пора напомнить…» (`LiveCalls.announce`, `urgent`); иначе VoIP-пуш `{ task: <id перезвона>, title }` тем же путём, что перезвон по заданиям (п. 4), поэтому приложение iPhone не менялось: id того же вида (16 hex), заголовок `X-Callback-Task` тот же, ядро само ищет id сначала среди перезвонов (`callbacks/context.ts`), потом среди заданий. Принятый звонок начинается с «Перезваниваю, как договаривались» и напоминания вместо приветствия, перезвон отмечается `answered`. Не ответили за 45 с — уведомление «Пропущенный звонок. Напоминаю: …». Ядро было выключено и время прошло больше двух часов назад, или VoIP не ушёл — сразу уведомление «Напоминаю: …». Ничего не дошло (`missed`, в том числе звонок, прерванный остановкой ядра) — напоминание в начале следующего звонка. Ближайшие три перезвона всегда есть в инструкциях звонка, чтобы Волна знала о них. Инструменты есть только с ключом APNs: без пушей перезвонить нечем. Первый живой звонок 26.09.2026: на «Ты можешь позвонить мне через пять минут» Gemini Flash Lite ответила «Сейчас наберу.» без вызова, проверка честности не знала слова «наберу», и Волна пообещала перезвон, которого не было. С тех пор «наберу», «звоню», «перезваниваю» — заявления (`delegation/honesty.ts`), и после такого ответа модель возвращается вызвать инструмент; в описании инструмента сказано, что позвонить сразу Волна не может. С 27.09.2026 перезвон без темы («позвони мне через пять минут») сначала спрашивает, о чём напомнить, как напоминание: признак `what` в вопросе Jev `missing` (`jev/questions.ts`) включает такой перезвон, и ядро просит Live спросить без модели; «просто перезвони» и «перезвони, как будет готово» не спрашивают. Замер на Jev 27.09.2026: 32 из 33 (11 фраз × 3, в том числе ответ на вопрос в следующей реплике); промах ниже порога уходит модели, у которой то же правило. Jev опаздывает (предел 800 мс) примерно в 4 % запросов; тогда модель со всеми инструментами ставила тему «просто перезвонить» сама (звонок 26.09.2026, 22:53; проба: 6 из 6, даже с флагом «только если сказал»). Поэтому `callback_schedule` без темы или с пустой темой («просто перезвонить», «звонок») в звонке сначала отвечает ошибкой `no_reason` с вопросом «О чём напомнить, когда позвоню?», ничего не записывая; после вопроса (своего или Волны: `askedInCall` по стенограмме, которую sideband даёт инструментам в `ToolContext.turns`) принимается любой ответ, и «ни о чём» тоже. Проба на запасном пути: 18 из 18 там, где нужен вопрос или ответ на него; «просто перезвони, напоминать не надо» тоже один раз спрашивает. В лог идут только способ доставки и статусы, без текста напоминания. Проверено только тестами; живьём на iPhone не проверено.

Лимит дописок (25.09.2026, звонок с итогом про тарифы оборвался ошибкой `invalid_value`: «Context append text must not exceed 500 tokens»). Всё, что ядро дописывает в идущий звонок (`session.commentary.append`, `session.instructions.append`), проходит `fitAppend` (`realtime/append-limit.ts`): оценка с запасом (кириллица ~2 знака на токен, латиница ~4), не больше 450, обрезка по концу предложения. Итог задания перед заметкой в звонок сжимается дешёвой моделью до одной-трёх фраз (`tasks/summary.ts`, модель сводок хода, тайм-аут 8 с); сжатый итог хранится в `Task.summary` и отдаётся в `tasks_list` вместе с полным. Без модели итог обрезается. Проверка на настоящем итоге: ~750 токенов → ~100, 0,9 с. Ручные ответы консоли не обрезаются намеренно (4k).

## 4p. Повторяющиеся задания

Сделано 06.10.2026 по сравнению с Hermes Agent (Nous Research): у него расписания на обычном языке, у Волны был только разовый перезвон. Код в `schedules/`, данные в `data/schedules.json`. Есть, когда есть «Работа» («Штурвал» на этой машине или через «Узел»); вид `call` — только с ключом APNs.

- **Что повторяется.** `work`: в срок ядро ставит задание «Работы» тем же `TaskRunner`, что `work_start`, с текстом расписания и строкой «Это регулярное задание «…» (по будням в 08:00), сегодняшний запуск: среда, 7 октября 2026». Итог приходит как у любого задания (4i): заметка в идущий звонок, одно уведомление на пачку или перезвон, если в расписании `callback: call` («перезванивай с итогом»). Проект и отдельная ветка задаются при создании, как у `work_start`; проект ищется один раз, по имени, только существующий. `call`: в срок ядро создаёт разовый перезвон на сейчас (`callbacks/`), дальше его ведёт `CallbackScheduler`: звонок с напоминанием, заметка в идущий звонок или уведомление.
- **Когда.** Время «ЧЧ:ММ» и дни недели (пусто — каждый день) в часовом поясе ядра `ASSISTANT_TIMEZONE`; переход на летнее и зимнее время держит местное время. Один таймер на ближайший срок, после каждого изменения взводится заново.
- **Пропуски.** Если задание прошлого срока ещё идёт, новый срок пропускается (`skipped_busy`): работа не копится. Если ядро было выключено и срок прошёл больше двух часов назад, он пропускается (`skipped_late`), меньше — запускается с опозданием. Сбой запуска пишется как `failed`. При любом исходе срок переходит на следующий.
- **Голос.** `schedule_create` — большая работа (`startsWork`): бэкенд предлагает её через `offer_work`, Волна говорит план («каждый будний день в восемь утра соберу сводку новостей по ИИ. Сделать?») и ядро записывает только после «да»; `readOnly` для расписаний не действует. Ответ: «Договорились: по будням в 08:00. Первый раз завтра в 08:00.» `schedules_list` (читает, есть карточка Jev) и `schedule_delete` (только по просьбе) есть в техкартах «Планы» и «Работа». Изменить — удалить и создать заново. Не больше 20 расписаний.
- **Маршрут.** 06.10.2026 на живом Jev по встроенным техкартам: повторяющиеся звонки-напоминания уходят в «Планы» (4 из 4), повторяющаяся работа в «Работу» (3 из 4; «каждый будний день собирай мои задачи из Штурвала» уходит в «Планы»: «задачи» Jev читает как напоминания). Предложение `schedule_create` доступно из любой техкарты. Живой бэкенд (те же модели, что в ядре) на пяти просьбах правильно составил вид, время, дни, проект и `callback`, показал список и удалил по просьбе. На iPhone не проверено.

## 4j. Приветствие

С 25.09.2026 первую фразу звонка выбирает код из набора (`greeting/phrases.ts`), без модели. С 23.09 по 25.09 её сочиняла дешёвая модель (`gemini-3.5-flash-lite`), и в живых звонках выходило неестественно: «Андрей, седьмой выход в эфир, лампа накалилась!», «Снова я на линии, слушаю», «Андрей, опять я на линии, что не так?». Модели запрещали повторять слова прошлых приветствий, и она уходила в экзотику; каждое четвёртое приветствие обязано было шутить про эфир и лампы; число звонков за день она озвучивала.

Теперь так, как отвечает на звонок близкий человек: коротко, повторы между звонками нормальны. Фраза зависит от давности прошлого звонка (первый звонок, до 15 минут назад — «Что-то забыли?», больше недели — «О, давно не слышались»), иначе от времени суток в зоне пользователя («Добрый вечер», ночью «Не спится?»). По имени примерно в трети звонков; имя берётся из памяти, из предложения «Зовут Андрей» в профиле или факте, на уровне cold не берётся. С 26.09.2026 отсылки к легенде выключены (`LORE_SHARE = 0` в `greeting/phrases.ts`, решение владельца): GPT-Live не произнёс ни одну по просьбе поздороваться, 0 из 6 звонков («Андрей, весь оркестр слушает», «Все агенты ещё тут, слушаю» — молчание или своя фраза, с обычными фразами после исправления «тин-тин» 4 из 4). Список оставлен, чтобы возвращать фразы по одной и смотреть в логах. До этого примерно в каждом пятом звонке, но не два раза подряд, вместо обычной фразы звучала отсылка к легенде (`about_wave`): «Волна в эфире, слушаю», «Оркестр в сборе, слушаю», сразу после разговора «Все агенты ещё тут, слушаю»; конструктору (`CREATOR` в `about-wave.ts`) ещё «Первый серийный на приёме». Без ламп (они из дизайна, а не из мира Волны) и без радиостилизации. Фразы без рода. Две последние дословно не повторяются. Весь набор и примеры выбора: `npm run greetings`.

В инструкции сессии уходит `greetingRule`: «скажи ровно „…“», затем, если есть, одной фразой, что работа готова (`results` из `tasks/context.ts`), или один короткий вопрос об открытой теме из памяти (`thread` из `memory/context.ts`), больше ничего. Готовая работа важнее темы: при обеих тема не выбирается и ждёт следующего звонка (4a, п. 5). Слова правила такие, что их не страшно услышать («работа готова», «открытая тема»), без «итогов фоновых заданий» и «нити». Это единственное место, где сказано, что говорить в начале обычного звонка: секции памяти и заданий только называют нить и итоги. Модель фразу не правит: если есть нить, код выбирает фразу без вопроса и, где в наборе есть замена, без «слушаю» (`Situation.thread` в `phrases.ts`; для ночи и первого звонка добавлены «Доброй ночи» и «Здравствуйте, это Волна», для этого `session-route.ts` сначала читает память, потом зовёт `forCall({ thread })`), иначе было бы «Не спится? Как сходили к врачу?». Раньше модели разрешалось «чуть поправить», и она склеивала «Да, добрый день, я на связи, слушаю»; до 26.09.2026 правило одновременно говорило «ничего не добавляя» и «спроси о нити», а просьба с телефона (`greetingInstruction` в `RealtimeClient.swift`) — «одна фраза»; теперь она только отсылает к правилу. Если пользователь заговорил первым («Алло»), Волна вместо фразы коротко отвечает ему; готовую работу упоминает одной фразой, о теме из памяти спрашивает позже в разговоре, если будет к месту (нить при этом всё равно считается поднятой). Звонок больше не ждёт модель (было 0,6–0,9 с), память в OpenRouter ради приветствия не уходит. Перезвон по заданиям здоровается по-своему (4i). `data/greeting.json` хранит время последних 30 звонков и последние 8 приветствий; звонок и фраза записываются только после того, как OpenAI принял звонок (`commit()` в `session-route.ts`): до 26.09.2026 неудачная попытка считалась звонком, и повтор слышал «Что-то забыли?». Принятый перезвон по заданиям фразы не имеет, но тоже записывается как звонок (`markCall()`), иначе звонок сразу после него получал неверную давность. В лог идёт только, была ли отсылка и имя, в замеры `greeting: phrase|off`. `GREETING=off` — запасное правило: «Да, слушаю», время суток только если голосовая модель его точно знает.

## 4k. Консоль ядра

С 25.09.2026, макет [design/volna-console.html](design/volna-console.html). Страница на Mac, где видно, что происходит с GPT-Live во время звонка, и где можно отвечать на делегирования вместо автомата. Отдельный сервер Hono на `127.0.0.1:25452` (`CONSOLE_PORT`; «ВОЛНА» на кнопках телефона), выключается `CONSOLE=off`. Ngrok смотрит на порт ядра, поэтому консоль снаружи не видна; заголовок `Host` проверяется от подмены DNS, меняющие запросы принимаются только с `Origin` самой консоли (`console/routes.ts`). Токена нет: доступ только с этого Mac.

1. `ConsoleHub` (`console/hub.ts`) заводит на каждый звонок `ConsoleCall` — первого участника sideband. В запись звонка идут события sideband (`in`), всё отправленное ядром (`out`, через `SidebandOptions.onSend`), отметки замеров (`mark`, через `CallTrace.onMark`; поэтому `CallTrace` создаётся и при `METRICS=off`, но на диск замеры пишутся только с `METRICS=on`) и решения консоли (`console`: контекст делегирования, ожидание, решение, вставка). Страница получает всё потоком SSE `/api/stream`, после переподключения — снимок идущих звонков.
2. Кто отвечает на делегирование: `ClientDelegate` после ожидания хвоста спрашивает `DelegationGate` консоли. «Авто» — как обычно; идущий автоматический ответ можно перехватить, тогда он отменяется. «Заготовка» — заранее заданный ответ (текст, сбой или молчание) уходит на следующее делегирование без Jev и модели, режим возвращается в «Авто». «Вручную» — делегирование ждёт ответа из консоли, без ответа через 20 с уходит автомату. Ручной ответ идёт в `session.commentary.append` как есть, без обрезки, ничего не исполняет; инструменты из консоли пока не вызываются (решение владельца 25.09.2026). Замеры: `client.manual`, `client.commentary.sent` с `path: manual`.
2a. Карточка делегирования показывает выбор Jev (быстрый инструмент, техкарта, класс с вероятностями), модель, которая думала над задачей (`модель gpt-5.6-luna ×2`: имя из `client.llm`, число кругов; после `escalate` следующая модель со стрелкой `↑`), и вызванные инструменты (с 26.09.2026 по просьбе владельца).
3. Вставка в контекст: `session.commentary.append`, `thinking.append` или `instructions.append` с `delegation_id` делегирования или `null`, до 4000 символов (больше лимита Live в 500 токенов, чтобы проверять и его).
4. История (`console/store.ts`): по окончании звонка запись уходит в `MEMORY_DIR/console/<время>-<звонок>.json`, хранятся последние 30 (решение владельца 25.09.2026), любую можно удалить со страницы. Вкладка «История» проигрывает звонок по таймлайну: дорожки «Вы», «Волна», делегирования и вставки, скорость 0,5–4×, переход к соседнему событию. Звука нет: он идёт мимо ядра. В отличие от замеров, запись содержит текст разговора; в лог текст по-прежнему не попадает.

5. «Сводка» и «Расходы» (с 27.09.2026, холст [design/canvas/console-dashboard](design/canvas/console-dashboard), решения владельца там же). С учётом расходов (4o) консоль открывается на «Сводке»; когда начинается звонок, страница сама переходит в «Эфир». «Сводка» (`GET /api/summary`, обновление раз в 15 с): состояние ядра, GPT-Live (итог последнего `POST /session`), OpenRouter (баланс), «Штурвал» (`check`), уведомлений и плагинов; траты и звонки за сегодня; медианы `speak` и `answer` за неделю из замеров; память; последние звонки с ценой; работа «Штурвала» без текста вопросов и итогов; предупреждения лога за сутки (`telemetry/health.ts` держит последние 500 в памяти). «Расходы» (`GET /api/costs?period=today|7d|30d|month`): итог и прогноз на месяц, «OpenAI по счёту» против секунд GPT-Live, баланс OpenRouter, столбики по дням по службам, доли служб, таблица моделей; строка модели открывает `/costs/<модель>` (`GET /api/costs/models/:model`): по дням, на что уходит, последние 200 вызовов со ссылкой на звонок. В «Истории» звонки названы началом первой просьбы владельца (60 знаков), цена звонка — кнопка у скорости, разбивка по службам по нажатию (`GET /api/calls/:callId/cost`); дорожки расхода на таймлайне нет: «История» для отладки (решение владельца 27.09.2026). Работа в «Штурвале» идёт по подписке и в деньги не входит.

Проверено тестами (поддельные сокет и модели) и на стенде в браузере с имитацией звонка; «Сводка», «Расходы» и цена звонка — тестами и на стенде с пробным учётом. С живым звонком не проверено: как Live ведёт себя при ручной паузе в 20 с, неизвестно.

## 4o. Учёт расходов

С 27.09.2026 (просьба владельца: сколько уходит денег на модели и на что). Каждый платный вызов — одна строка JSON в `MEMORY_DIR/usage/YYYY-MM.jsonl` (`usage/ledger.ts`): время, служба (`voice`, `delegation`, `memory`, `jev`, `service`), назначение, модель, id звонка или `null`, токены входа, из кэша, выхода и размышлений, секунды, цена в долларах. Текста, аргументов и ключей в записи нет. Файлы не чистятся: за месяц это сотни килобайт. Считается с момента внедрения, прошлое не заполняется (решение владельца 27.09.2026).

- OpenRouter (делегирование, поиск, разбор памяти, «сон», пересмотр характера, названия звонков, сводки заданий, Jev через OpenRouter): запрос с `usage: { include: true }`, цена из `usage.cost` как есть. `chatModel` пишет запись сам (`meter` с назначением), `askStructured` и `jevClient` — через `meter` в настройках.
- GPT-Live: цены в ответе нет, только секунды (`session.usage.updated` раз в ~15 с, итог в `session.closed.usage.seconds`). Запись одна, когда звонок кончился: секунды × `LIVE_PRICE_PER_MINUTE` / 60 (gpt-live-1: $0,05 за минуту, посекундно).
- Звонок и назначение приходят из контекста (`AsyncLocalStorage`, `usageScope`): участники sideband обёрнуты `scopedListener` с id звонка, поэтому всё, что они начали (делегирование, Jev, поиск, таймеры), числится за звонком; разбор памяти, «сон» и пересмотр характера после звонка тоже. Назначения Jev (`jev_route`, `jev_honesty`, `jev_goodbye`) задаёт место вызова.
- Сверка: баланс и траты ключа OpenRouter за день и месяц (`/api/v1/credits`, `/api/v1/key`, раз в 5 минут, тем же ключом). OpenAI — Costs API (`/v1/organization/costs`, только по дням UTC, раз в час) ключом администратора `OPENAI_ADMIN_KEY`; ключ только читает счёт и не попадает ни в лог, ни в ответ консоли; `OPENAI_COSTS_PROJECT` сужает счёт до проекта. Без ключа плитка «OpenAI по счёту» пустая, голос считается по секундам.
- Работа в «Штурвале» (Claude и Codex) по подписке: денег не считаем.
- Не учитываются: `npm run dream`, `npm run persona` и прочие команды CLI (у них свой ключ, звонка нет).

Проверено тестами (`usage/usage.test.ts`, `console/dashboard.test.ts`) и одним настоящим запросом к OpenRouter (поле `cost` в ответе, баланс и траты ключа). Живым звонком не проверено: совпадёт ли сумма по секундам со счётом OpenAI.

Ниже в этом разделе названия команд прежнего протокола 1 (T3 0.0.42) соответствуют так: `thread.create` + `thread.turn.start` → `orchestration.launchThread`, `thread.turn.start` в существующий тред → `message.dispatch`, `thread.turn.interrupt` → `run.interrupt`, `thread.user-input.respond` → `runtime-request.respond`, активности `user-input.requested`/`approval.requested` → заявки `runtimeRequests`. `HELM_URL` по умолчанию `http://127.0.0.1:3783`, порт в `~/.helm/userdata/server-runtime.json`. Токен `Authorization: Bearer` выдаёт владелец один раз из репозитория `t3code`: `node apps/server/dist/bin.mjs auth session issue --base-dir ~/.helm --label volna --ttl 30d --token-only` (права административные, узких «Штурвал» не выдаёт). Токен не пишется ни в лог, ни на диск ядра. Id треда, сообщения и команды создаёт ядро (UUID); команды идемпотентны по `commandId`. Схемы — зеркало нужных полей; элемент хода с полем чужого типа не роняет разбор (живая проверка 05.10.2026: `input` бывает объектом). Перед командами, не чаще раза в минуту, ядро проверяет версию: мажорная версия 0, протокол оркестрации 2. Иначе `helm_incompatible` и ни одной команды; остановка хода проходит всегда. При старте в логе `helm.ready` или `helm.unavailable`.
2. Исполнитель (`helm/worker.ts`, `helmWorker`). Проект «Штурвала» для папки `HELM_PROJECT_DIR` (по умолчанию `~/Documents/Volna Work`) находится по `workspaceRoot` или создаётся. Каждое задание — новый тред с названием задания. Модель: `HELM_INSTANCE` (`claudeAgent` по умолчанию, `codex` или свой инстанс) и `HELM_MODEL`; если модель не задана, берётся модель проекта при том же инстансе, иначе `claude-opus-5-5` у Claude (с 26.09.2026, до этого Fable 5.1); у Codex своей модели по умолчанию нет с 05.10.2026 (была `gpt-6-astra`), берётся модель сервера. Модель, выбранную у проекта, ядро не трогает. Новые проекты (и проект «Работы», если его ещё нет) ядро создаёт сразу с этой моделью (`defaultModelSelection` в `project.create`), чтобы и в окне «Штурвала» они открывались на ней, а не на Fable 5.1 по умолчанию «Штурвала». Режим `HELM_RUNTIME_MODE`: `auto` по умолчанию, `auto-accept-edits` или `approval-required`; `full-access` ядро не включает. Задание уходит агенту как есть, без добавок (решение владельца 25.09.2026): как его сформулировала модель, так и отправляется. Id треда пишется в `Task.helmThread`. Опрос раз в 2,5 с; новые активности и законченные реплики агента идут в журнал хода (4i). Ход `completed` без открытого вопроса — задание готово, итог — последний ответ агента. `error` и `interrupted` — сбой (`helm_turn_error`, `helm_interrupted`); пять опросов подряд без ответа — `helm_lost`. Отмена или тайм-аут шлют `thread.turn.interrupt`; тред остаётся в «Штурвале». С 26.09.2026 ([task-sync.md](task-sync.md), этап 1): id треда ядро создаёт само и пишет в задание с `helmPending: true` до `thread.create`, флаг снимается, когда «Штурвал» подтвердил тред; сбой между ними не оставляет треда без задания. Задание с `helmThread` переживает перезапуск ядра: `TaskStore` (`resumable`) оставляет его `running`, `TaskRunner.resume()` снова отдаёт его исполнителю, и тот продолжает опрос того же треда, ничего не начиная заново; `helmPending` без треда в «Штурвале» — `failed/interrupted`. Предел задания `HELM_TASK_MAX_MINUTES` (120) от `startedAt` вместо 10 минут; тред без новых активностей, сообщений и смены хода дольше `HELM_STALL_MINUTES` (20) — `failed/helm_stalled` и `thread.turn.interrupt`; ожидание ответа или разрешения зависанием не считается.
3. Вопросы агента. Активность `user-input.requested` ядро разбирает как «Штурвал» (`derivePendingRequests`). Каждый новый вопрос один раз приходит заметкой в идущий звонок (`LiveCalls.announce`): задание, вопрос, варианты и id задания; Волна задаёт его своими словами. Пока вопрос открыт, у задания `waiting: { kind: 'question', text }` (видно в `tasks_list`). Ответ голосом — `work_answer` (`act`, в техкарте «Работа»): id задания, id треда или ничего (единственный ждущий вопрос). Уходит `thread.user-input.respond` с ответами по id вопросов, как из окна «Штурвала».
4. Разрешения. Голосом не даются никогда; инструмента для них нет, и «Узел» не пропускает `decision`. Запрос ждёт в «Штурвале» (на Mac или в мобильном приложении), Волна одной фразой говорит, что работа ждёт разрешения там (карточка подтверждений на телефоне Волны удалена 05.10.2026). У задания `waiting: { kind: 'approval' }`.
5. Проекты (`helm/projects.ts`, `pickProject`). `work_start` принимает `project`, `newProject` и `worktree`. Без проекта — «Волна: Работа» (`HELM_PROJECT_DIR`). Существующий ищется по названию или имени папки: точно, по подстроке, затем по согласным после транслитерации («колл ассистент» → CallAssistant, «драфт вол» → draft-wall); несколько совпадений или ни одного — список проектов, модель переспрашивает. Новый проект (`newProject: true`, только по просьбе) — всегда новая пустая папка в `HELM_NEW_PROJECTS_DIR` (по умолчанию `~/Documents`); существующая папка проектом голосом не становится (`folder_exists`): это доступ к файлам, его даёт владелец в окне «Штурвала». Проект задания хранится в `Task.helmProject`. Живая проверка 25.09.2026: тред в CallAssistant по «колл ассистент», ответ агента за 9 с. `worktree: true` (только по просьбе пользователя): `work_start` проверяет, что папка проекта — git-репозиторий (иначе `not_a_repository`, задание не создаётся), с 05.10.2026 исполнитель запускает тред с `workspaceStrategy: { type: 'worktree', baseRef: 'HEAD', branch: 'wave/<id задания>' }`, и worktree создаёт сам «Штурвал» (до этого ядро делало `git worktree add` само, `helm/worktree.ts`, а в облаке — «Узел»). Отказ запуска с веткой — `worktree_failed`. Worktree ядро не удаляет. Живьём не проверено.
6. Треды (`helm/tools.ts`). `work_threads` (читает, есть карточка Jev): живые треды, состояния `needs_you|working|failed|idle`, и названия всех проектов (`projects`), чтобы проект не искали среди тредов. `work_send` (`act`, с пересказом и «да»): сообщение в существующий тред. `work_stop` (`act`, с 26.09.2026, с пересказом и «да»): остановить ход в любом треде, в том числе в собственном треде владельца (`thread.turn.interrupt`, статус меняется, когда «Штурвал» покажет `interrupted`); тред идущего задания Волны отменяет само задание. `work_answer` на вопрос, на который уже ответили (на компьютере или в мобильном «Штурвале»), отвечает `already_answered` и фразой «На этот вопрос уже ответили.» `work_add` (`act`, без пересказа, с 26.09.2026): слова владельца в идущую работу из `work_start` по id задания («а ещё посмотри PDF», ответ на вопрос Волны о работе). Оба пишут и в тред с идущим ходом (steer): с 05.10.2026 это `message.dispatch` с `deliveryIntent: steer`, и «Штурвал» сам кладёт сообщение в идущий запуск или, если тот уже кончается, новым (до этого T3 0.0.42 принимал `thread.turn.start` в такой тред; живьём не проверено). Не пишут, пока агент ждёт ответа на вопрос (`agent_asks`, сначала `work_answer`) или разрешения (`waiting_permission`), как и окно «Штурвала». У работы запоминается `steer` (время и ход); исполнитель (`helm/worker.ts`), увидев конец этого хода, ждёт `steerGraceMs` (8 с): начался новый ход с добавкой — итог берётся из него, нет — из прежнего. До 26.09.2026 занятый тред не трогали (`thread_busy`). Новый тред только через `work_start`: у него есть ход работы, вопросы и итог (до 26.09.2026 был отдельный `t3_thread_start` без слежения, а `work_threads` и `work_send` назывались `t3_threads_list` и `t3_thread_send`). Как выбирать между новой работой и существующим тредом, написано в техкарте `core/skills/work/SKILL.md` (до 26.09.2026 отдельная `code`): «дай агенту задание» — сразу новая работа, без проекта — общая папка. Правила бэкенда — `BACKEND_AGENT_WORK_RULES` в `persona.ts`.

В лог попадают только id заданий, статусы, коды ошибок и версия «Штурвала». Живьём 25.09.2026 через код ядра (без звонка): задание в «Волна: Работа» с итогом за 13 с, вопрос агента заметкой и ответ `work_answer` за 33 с, тред в проекте CallAssistant. ## 4n. Один список работы: задания Волны и треды «Штурвала»

С 26.09.2026, план и решения владельца: [task-sync.md](task-sync.md). `work-sync/sync.ts` (`WorkSync`, есть при `HELM_TOKEN`) держит в памяти один список: задания Волны из `tasks.json` и все неархивные треды «Штурвала» из `GET /api/orchestration/shell`. Файла у реестра нет: он целиком собирается из этих двух источников. Синхронизация только читает (`shell`, `threads/:id`) и не шлёт команд (тест). Опрос раз в 10 с, пока идёт звонок или есть `working`/`needs_you`, иначе раз в 60 с.

- Запись: `id` (`helm:<тред>`, у задания без треда `task:<id>`), `origin` (`volna` или `owner`), `task`, `thread`, `project`, `title` (≤ 120), `status`, `waiting`, `progress`, `result` (≤ 600), `error`, `updatedAt`, `finishedAt`, `stale`. Связь задания и треда только по `task.helmThread`.
- Статус (`work-sync/status.ts`, общее правило `threadState` с `work_threads`): вопрос или разрешение — `needs_you`; ход `running` или сессия `running`/`starting` — `working`; `error` — `failed`; закончен у собственного треда — `idle`. Задание Волны держит свои `queued`/`done`/`failed`/`cancelled`; идущее задание без треда в `shell` (и без `helmPending`) — `gone`. Законченное задание, продолженное владельцем в том же треде, остаётся `done`, а запись показывает `working`.
- Снимок треда с более старым `updatedAt` не применяется. «Штурвал» не отвечает: список прежний, `stale: true`; `helm_unauthorized` останавливает опрос; `helm_incompatible` только помечает список. Одна строка лога `sync.helm.<состояние>` на смену состояния.
- У собственных тредов наружу только заголовок, проект, статус и вид ожидания: ни текста вопроса, ни фразы хода, ни итога.
- Вопрос или разрешение в собственном треде, пока идёт звонок, один раз уходит заметкой (`ownerQuestionNote`, `ownerApprovalNote`, не больше трёх за опрос); ответ голосом тем же `work_answer` по id треда. Вне звонка уведомления нет. Вопросы заданий Волны по-прежнему объявляет `helmWorker`.
- `tasks_list` добавляет `threads` (собственные треды: идущие, ждущие и за сутки, до 8) и `helm` с `asOf`, если «Штурвал» не ответил. `GET /work` с токеном ядра отдаёт `{ access, asOf, items }` (до 20, то же окно в сутки) для будущего экрана; телефон пока читает `GET /tasks` (этап 3 ждёт доски на холсте).
- Смысловой дубль (`work-sync/similar.ts`): перед предложением `work_start` ядро ищет идущую работу того же проекта с похожим заголовком (основы слов) и дописывает к плану предложение дописать туда (`similarCommentary`: в задание Волны через `work_add`, в собственный тред через `work_send` с пересказом). Сам ничего не сливает.

В лог только id, статусы и коды; тест проверяет, что заголовки, ход и итоги туда не попадают. Проверено только тестами на поддельном T3; живьём не проверено.

## 4m. Плагины и MCP-серверы

Плагин (формат Claude Code, устройство в [skills.md, 7](skills.md#7-плагины)) приносит техкарты и MCP-серверы. `main.ts` при старте зовёт `startPlugins`: серверы плагинов со статусом `enabled` поднимаются параллельно, каждый не дольше 20 с (`MCP_CONNECT_TIMEOUT_MS`), упавший сервер только пишется в лог (`plugin.mcp_failed`, `plugin.mcp_skipped`, `plugin.needs_enable`), ядро стартует без его инструментов. Инструменты из `tools/list` добавляются в реестр; одноимённые с уже существующими и служебными пропускаются.

- **Клиент** (`plugins/mcp-client.ts`). Свой, без `@modelcontextprotocol/sdk`: ядру нужна только клиентская половина (`initialize`, `tools/list` с постраничной выдачей, `tools/call`, `notifications/cancelled`, ответ на `ping`). stdio: процесс в папке плагина, окружение только `PATH`, `HOME`, `USER`, `LANG`, `TMPDIR` и подобные плюс `env` из `.mcp.json`, stderr не читается. HTTP: POST с `Accept: application/json, text/event-stream`, ответ JSON или SSE, `Mcp-Session-Id`.
- **Паспорт.** `Tool.jsonSchema`: схему задаёт сервер, `definitions()` отдаёт её вместо `z.toJSONSchema(parameters)`. `ToolRegistry.only` понимает маску `префикс*` из `allowed-tools`.
- **Вызов.** Тайм-аут 30 с (`MCP_CALL_TIMEOUT_MS`), сигнал вызова отменяет запрос. Результат — текстовые части (иначе `structuredContent` как JSON), не длиннее 8000 знаков. Ошибки структурированы: `tool_error`, `mcp_error`, `mcp_timeout`, `cancelled`, `plugin_unauthorized`, `plugin_offline`, `plugin_disabled`. Упавший процесс или истёкшая HTTP-сессия переподключаются при следующем вызове, не чаще раза в 30 с.
- **Лог.** Только имя плагина, сервера и инструмента, транспорт, число инструментов и вид сбоя. Никогда: заголовки, значения переменных, аргументы и результаты.
- **Доступ.** Включение (`enable`) есть только в `npm run plugins` на Mac; голосового инструмента и HTTP-маршрута для него нет. После `enable` нужен перезапуск ядра; `disable` действует сразу.

Проверено тестами (поддельный stdio-сервер) и вручную на удалённом сервере context7 во временной папке; в звонке не проверено.

## 5. Как добавить инструмент

1. Файл `src/assistant/tools/<name>.ts`:

   ```ts
   import { z } from 'zod';
   import { defineTool } from './registry.ts';

   export const weather = defineTool({
     name: 'weather',
     effect: 'read',       // read | write | act; act только после кнопки на телефоне
     // startsWork: true   большая работа: модель предлагает её через offer_work, ядро запускает после «да»
     // always: true       нужен в каждом звонке, вне техкарт (завершение звонка, техкарты)
     // jev: { when, args }  только для read без свободного текста: быстрый путь без LLM
     description: 'Current weather for a city. Call when the user asks about weather.',
     parameters: z.object({ city: z.string().describe('City name') }),
     async execute({ city }, context) {
       // context: callId, signal (отменяется при закрытии звонка), log, timeZone, now()
       return { city, temperature: 21 };
     }
   });
   ```

2. Строка в `defaultTools()` в `tools/index.ts` и имя в `allowed-tools` техкарты, к которой инструмент относится (`core/skills/<имя>/SKILL.md`; новая встроенная техкарта: папка с `metadata.system: "true"`, `title` и, если нужно, `tier`). Инструмент без техкарты модель видит только в маршруте «все инструменты».
3. Тест рядом: `registry.call(...)` с `silentLogger`; при внешних запросах передавать `fetch` через параметры инструмента, а не через глобальный.
   Инструмент телефона: `runsOn: 'device'` в `device.ts` плюс ветка в `DeviceToolRunner` и `DeviceToolStore` в приложении, тест в `ios/Tests/Unit/DeviceToolRunnerTests.swift`.
4. Секреты инструмента только в `.env` через `config.ts`. Аргументы и результаты не логировать.
5. Имя инструмента попадает в инструкции автоматически; описание читает модель, пишите его как правило «когда звать». `defineTool` проверяет паспорт: карточка Jev только у `read` и только с настоящими аргументами, имена `escalate`, `offer_work`, `start_offered_work` заняты маршрутом.
